# 第 1 轮：他机下线后状态在「离线 / 附近 / 尝试连接」间反复跳动

> 时间: 2026-06-30

## 用户提问

他机刚刚下线了，本来也确实提示已经下线，但是过了一会又回到附近中了，明明对方电脑还没开机，再过一会显示他机离线了，正在尝试连接。

## 背景与分析

### 现象还原

用户侧观察到的状态路径：

1. 他机下线 → 先正确提示「已下线 / 离线」
2. 过一会儿设备又回到「附近」
3. 再过一会儿变回「离线」，并出现「正在尝试连接 planarcat-win11」

截图中右侧连接概览显示 `192.168.0.28:19877`、`最近活跃 5秒前`，设备页却是 `0/0` 已配对、设备在「离线」区——说明**局域网发现列表里短暂出现过这台设备，但并没有真正连上**。

### 前端分区逻辑

设备三区划分依赖 `discoveredOnLan`：

- **已配对**：`status === "connected"`
- **附近**：`discoveredOnLan === true` 且未连接
- **离线**：可信设备但不在 `lan_devices` 中

`buildDevices` 只要设备出现在 `lanDevices`，就会把 `lastSeen` 设为 `new Date()`，因此「最近活跃 5秒前」实际含义是「5 秒前某次探测/mDNS 认为它在线」，而非对方真的在 5 秒前活跃。

### 后端在线判定混用三种信号

| 信号 | 实际在问什么 | 语义是否正确 |
|------|-------------|-------------|
| mDNS 广播/移除 | 局域网里有没有 PlanarClip 服务注册 | ✅ 角色级（但有过期缓存） |
| TCP 端口探测（每 8 秒） | 这个 IP 上有没有进程在听 19876/19877 | ❌ 机器/端口级 |
| 连接断开事件 | 会话是否结束 | ✅ 角色级（仅对已连接设备） |

关键问题：**`discover_trusted_peers_by_tcp_probe` 与 `reconcile_lan_devices` 大量使用裸 TCP 探针**。只要同 IP 上有任意东西响应端口（路由残留、DHCP 换主、别的服务占端口、网络重置后的抖动），设备就会被重新加入 `lan_devices`，UI 移入「附近」。

### 状态机时序（推断）

```
他机关机/断连 → mDNS Removed 或 reconcile prune → 离线 ✓
     ↓ ~8s
TCP 探针 last_ip 成功（误判）→ 加入 lan_devices → 附近
     ↓
mDNS 陈旧 Added 或 auto_connect 触发 → 正在尝试连接
     ↓
握手失败 + reconcile 探针失败 → prune → 离线
```

用户剪贴板历史中可见 `netsh winsock reset` 等网络重置命令，可能加剧探针结果抖动。

## 建议与回答

这是**探测策略偏宽松 + 多机制不同步**导致的状态闪烁，不是 UI 单纯显示错误。

当前 TCP 探针实现（`probe_tcp_reachable`）只检查 `TcpStream::connect` 是否成功，不验证 PlanarClip 协议。Listener 侧虽有「不完整握手 ≈ 探针误连」的 debug 日志，但**发起探测的一侧从未做协议校验**。

## 本轮要点

- 问题已复现多次，根因是「机器/端口可达」被误当作「PlanarClip 在线」
- 裸 TCP 探针是主要误判来源；mDNS 陈旧记录会加剧闪烁
- `lastSeen` 在前端每次列表刷新时重置，加剧用户困惑
- 需要从架构层替换探测方式，而非继续调 timeout/interval
