# 第 8 轮 · MVP 精简 — 降低首次交付复杂度

> **背景**：当前执行方案包含 4 个 Phase，需要评估哪些模块可推迟，优先产出一版可用的 MVP。

---

## 用户提问（原文）

> 目前的待执行方案复杂度如何？我需要先产出一版MVP，有没有哪些模块可以先精简，或者移到未来版本？

---

## 当前方案复杂度评估

| Phase | 内容 | 周数 | 累计 | 复杂度 |
|:---|:---|:---|:---|:---|
| 1 | 文本同步 + 加密 + 信令 + SQLite + 托盘 + 配对 + 前端 + CI | 4–6 | 4–6 | 🔴 高 |
| 2 | 图片 + 文件同步 + 分块传输 | 3–4 | 7–10 | 🟡 中 |
| 3 | 多设备 + 重连 + TURN | 3–4 | 10–14 | 🟡 中 |
| 4 | mDNS + 通知 + 主题 + 安装包 | 3–4 | 13–18 | 🟢 低 |

**Phase 1 的问题**：虽然是"MVP"，但塞进了太多东西。需要在 Phase 1 内部进一步砍。

---

## 精简建议

### 绝对保留（MVP 核心）

| 模块 | 理由 |
|:---|:---|
| 剪贴板文本监控 + 写入 | 核心价值，无可替代 |
| WebSocket 信令（嵌入式/公共实例） | 两台设备必须能通信 |
| WebRTC 数据通道（单对单） | 数据传输通道 |
| 系统托盘图标 + 基础菜单 | 后台常驻的底线体验 |
| 配对码 + 密钥交换 | 安全连接的前提 |

### 可精简 / 推迟

| 模块 | 当前 Phase | 建议 | 理由 |
|:---|:---|:---|:---|
| SQLite 存储 | Phase 1 | **→ 推迟到 Phase 2** | MVP 用 JSON 文件存历史即可 |
| Noise IK 完整加密 | Phase 1 | **→ 降级为 WebRTC DTLS + 简易密钥验证** | WebRTC 本身已有 DTLS 加密传输，MVP 可暂不加应用层加密 |
| 完整 React 前端 | Phase 1 | **→ 降级为单页 HTML** | 配对页只需一个输入框，Dashboard 只需状态显示 |
| 独立信令服务器二进制 | Phase 1 | **→ 嵌入 Tauri 或使用公共实例** | 减少部署负担 |
| CI 双平台构建 | Phase 1 | **→ 推迟到 Phase 2** | 手动验证先行 |
| 图片同步 | Phase 2 | **→ 不动，仍在 Phase 2** | |
| 文件列表同步 | Phase 2 | **→ 推迟到 Phase 3** | CF_HDROP/NSPasteboard 是已知难题 |
| 文件分块传输 | Phase 2 | **→ 仅做小文件（<5MB 全量）** | 分块协议开发量可观 |
| 多设备（N>2） | Phase 3 | **→ 不动，仍在 Phase 3** | |
| TURN 回退 | Phase 3 | **→ 不动，仍在 Phase 3** | LAN + STUN 先覆盖大部分场景 |
| 原生通知 | Phase 4 | **→ 不动** | |
| mDNS 发现 | Phase 4 | **→ 不动** | |
| 安装包签名 | Phase 4 | **→ 不动** | |

---

## 精简后的 Phase 划分

### Phase 1 · MVP（精简后）

> 目标: 两台设备配对，文本剪贴板双向同步，托盘常驻
> 预计: **2–3 周**（原 4–6 周）

```
┌─────────────────────────────────────────────┐
│                Phase 1 MVP                   │
│                                              │
│  arboard ──→ WebRTC(DTLS) ──→ 对端 arboard │
│     │              │                │        │
│  文本监控     公共信令实例       文本写入     │
│     │                            │          │
│  托盘图标 ←────────────────── 配对码输入    │
│                                              │
│  暂不含: SQLite / Noise / 图片 / 文件 / CI  │
└─────────────────────────────────────────────┘
```

| 任务 | 说明 |
|:---|:---|
| Tauri 2 脚手架 | 最简配置 |
| 剪贴板文本监控 | arboard, 500ms 轮询, blake3 去重 |
| 剪贴板文本写入 | 接收远程内容后写入本地 |
| 信令连接 | 内置公共信令实例地址，WebSocket 直连 |
| WebRTC 单对单 | 数据通道，利用 DTLS 加密传输 |
| 6 位配对码 | 生成 + 输入 + 密钥交换（基础版）|
| 自写入回环抑制 | AtomicBool + last_hash |
| 系统托盘 | 图标 + 基础菜单（显示/退出）|
| 单页前端 | 输入配对码 + 显示连接状态 |

### Phase 2 · 安全与持久化

> 预计: 2–3 周

- [ ] SQLite 存储（历史 + 设置 + 密钥）
- [ ] Noise IK 应用层加密
- [ ] 图片同步（≤5MB 全量传输）
- [ ] CI 双平台构建

### Phase 3 · 文件与多设备

> 预计: 3–4 周

- [ ] 文件列表同步（平台特定代码）
- [ ] 大文件分块传输
- [ ] 多设备连接管理
- [ ] 断线重连
- [ ] TURN 回退

### Phase 4 · 打磨与发布

> 预计: 3–4 周（不变）

- [ ] mDNS LAN 发现
- [ ] 原生通知
- [ ] 完善前端（多页面）
- [ ] 暗色/亮色主题
- [ ] 安装包 + 签名
- [ ] 剪贴板安全过滤
- [ ] 用户文档

## 前后对比

| 指标 | 原方案 | 精简后 | 变化 |
|:---|:---|:---|:---|
| Phase 1 周数 | 4–6 | **2–3** | -50% |
| Phase 1 任务数 | 11 | **7** | -36% |
| 到可用 MVP 时间 | 4–6 周 | **2–3 周** | 快一倍 |
| 加密 | Noise IK | **DTLS（WebRTC 内置）** | 降级 |
| 存储 | SQLite | **JSON 文件** | 降级 |
| 前端 | React SPA | **单页 HTML** | 降级 |
| 信令服务器 | 独立二进制 | **公共实例** | 免部署 |

---

## 📌 本轮要点

- Phase 1 塞了太多东西，内部再砍 4 项：SQLite → 推迟、Noise → 降级 DTLS、React → 单页 HTML、独立信令 → 公共实例
- **2–3 周可交付可用的文本同步 MVP**
- 被砍的模块自然流向后续 Phase，不丢失
- 核心链路不变：监控 → 加密 → 传输 → 写入 → 去重
