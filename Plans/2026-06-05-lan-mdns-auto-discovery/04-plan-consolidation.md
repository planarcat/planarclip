# 第 4 轮：整理 6.5 主题的待执行方案

> 时间: 2026-06-21 13:41

## 用户提问

6.5整理一个待执行方案出来

## 背景与分析

6.5 主题目前已有三轮讨论：

- 第 1 轮确定采用 mDNS 做局域网自动发现，并保留与旧的配对码 / relay 模式共存。
- 第 2 轮细化了局域网连接流程：双向可发现、单向发起连接、响应方展示 6 位配对码、发起方输入后建立连接。
- 第 3 轮给出了一版较完整的 MVP 设计稿，覆盖 mDNS、TCP 帧协议、握手消息、可信设备持久化与自动重连。

但现有文档的问题是：

1. 设计内容已经足够完整，但缺少一份站在“当前仓库状态”上的执行清单；
2. 第 3 轮更像详细设计说明，不够适合作为后续直接执行和验收的工作底稿；
3. 经过后续代码演进，局域网发现、局域网直连、可信设备自动接受等主链路已经有较多实现，因此新的待执行方案应该聚焦“剩余收尾项”，而不是重新规划一遍已完成内容。

因此，本轮目标不是重新发明一套 LAN 方案，而是把 6.5 主题整理成一份可直接执行、可验收、能反映当前真实进度的 `execution-plan.md`。

## 建议与回答

建议将 6.5 主题的待执行方案整理为“已完成基线 + 待执行 Phase”的结构：

### 已完成基线（不再重复作为主任务）

- mDNS 服务注册与局域网设备发现主链路已存在；
- 前端已有局域网设备列表、连接按钮、连接请求弹窗、配对码输入弹层；
- 后端已有 `get_lan_devices`、`connect_lan`、`submit_pairing_code`、`reject_connection` 等命令；
- 已有 TCP 直连握手、可信设备持久化、已配对设备自动接受；
- 已有直连后的文本剪贴板同步主链路。

### 待执行内容应聚焦

1. **用户体验收口**
   - 把局域网连接相关的成功 / 警告 / 错误提示改成自然中文；
   - 明确区分“发现设备”“正在连接”“等待输入配对码”“连接成功”“连接失败”“对方拒绝”等状态；
   - 避免在 UI 直接暴露底层错误、英文异常或程序术语。

2. **连接状态与异常处理补强**
   - 补齐配对码过期、主动取消、重复点击连接、连接中断后的状态恢复；
   - 统一前后端事件语义，避免 UI 停留在旧状态；
   - 验证可信设备自动重连与首次连接提示是否一致。

3. **发现与连接链路稳定性验证**
   - 验证 mDNS 设备上下线时列表更新是否稳定；
   - 验证双设备在同一局域网内的首次配对、再次连接、文本双向同步；
   - 验证拒绝连接、配对码错误、对端离线等异常场景。

4. **文档与主题治理**
   - 为 6.5 生成正式 `execution-plan.md`；
   - 后续执行完成后，再由执行流程补写 `COMPLETED.md` / `UNEXECUTED.md`；
   - 与已锁定的 6.4 主题形成清晰分工：6.4 负责方向收敛，6.5 负责 LAN 落地与收尾。

## 本轮要点

- 本轮不改源码，只整理 6.5 的待执行方案文档。
- 新的执行方案应基于“当前代码已实现大半主链路”的事实来编排。
- 待执行重点不是重新做架构，而是做用户体验收口、异常处理补强、真实联调验证与文档归档。
