# 局域网 mDNS 自动发现与直连收尾 — 待执行方案

> 生成时间: 2026-06-21
> 基于讨论: [01-lan-auto-discovery-tech-selection.md](01-lan-auto-discovery-tech-selection.md) | [02-lan-connection-flow-design.md](02-lan-connection-flow-design.md) | [03-mvp-implementation-plan.md](03-mvp-implementation-plan.md) | [04-plan-consolidation.md](04-plan-consolidation.md)

## 需求概述

围绕 PlanarClip 的 6.5 主题，将“局域网内自动发现设备并完成直连同步”的方案整理为当前可执行的落地计划。

本主题不再从零设计 LAN 方案，而是基于仓库现状推进剩余工作：在已有 mDNS 发现、TCP 直连握手、配对码校验、可信设备持久化和文本同步主链路的基础上，补齐用户体验、异常处理、联调验证与文档收尾，使 LAN 模式达到可交付状态。

## 当前进度判断

### 已完成基线

- mDNS 服务注册与局域网设备发现主链路已具备；
- TCP 监听与局域网直连握手主链路已具备；
- 发起方输入配对码、响应方展示连接申请与 6 位码的 UI / 事件主链路已具备；
- `trusted_peers` 已支持已配对设备后续自动接受；
- 直连后的文本剪贴板同步主链路已具备。

### 当前仍待收尾的内容

- 用户侧提示文案还不够自然，部分错误与状态表达仍偏技术化；
- 首次连接、重连、拒绝、超时、失败等场景的状态收口仍需统一；
- 需要补一轮以真实设备为中心的局域网联调验证；
- 需要在 Plans 中形成可执行、可验收、可归档的主题文档闭环。

## 技术决策

| 决策项 | 选择 | 理由 | 来源轮次 |
|--------|------|------|----------|
| 设备发现方式 | mDNS 自动发现 | 无中心服务、跨平台、适合 LAN 内零配置发现 | 第 1 轮 |
| 连接模式 | LAN 发现后 TCP 直连 | 同局域网内不再依赖 relay，中继链路仅保留兼容入口 | 第 1、2 轮 |
| 配对交互 | 响应方生成 6 位临时配对码，发起方输入验证 | 与蓝牙式配对相似，用户易理解，安全边界更清晰 | 第 2 轮 |
| 握手协议 | `ConnectRequest -> AuthCode -> AuthResult` | 足够简单，便于 MVP 快速落地 | 第 2 轮 |
| 配对码策略 | 临时随机 6 位码，短时有效 | 避免长期固定码被重放，符合局域网首次配对场景 | 第 2、3 轮 |
| 可信设备策略 | 首次配对后持久化 `trusted_peers`，后续自动接受 | 降低重复输入成本，形成基本重连体验 | 第 3 轮 |
| 数据通道 | 直连后复用现有文本同步消息协议 | 减少协议分叉，控制实现复杂度 | 第 1、3 轮 |
| 当前产品边界 | 先做 LAN 可用，不纳入跨网、STUN/TURN/NAT 穿透 | 保持范围收敛，聚焦可交付 MVP | 第 1、3、4 轮 |
| 执行重点 | 补体验、补异常、补验证，不重复做已完成主链路 | 当前仓库已具备大部分基础实现 | 第 4 轮 |

## 实现步骤

### Phase 1：用户可见状态与文案收口
- [ ] 盘点 LAN 流程中的所有成功、警告、失败提示
- [ ] 将局域网连接相关提示统一为自然中文，不直接暴露程序术语
- [ ] 明确区分“发现设备 / 正在连接 / 等待输入配对码 / 已连接 / 已断开 / 已被拒绝 / 输入错误 / 已超时”等状态
- [ ] 统一首次连接与自动重连的提示口径
- [ ] 确保前端弹层关闭、取消操作与状态文本一致

### Phase 2：异常处理与状态机补强
- [ ] 梳理连接发起方与响应方的完整状态流转
- [ ] 补齐配对码过期、对端拒绝、对端离线、重复点击连接、连接中断等场景处理
- [ ] 统一前后端事件命名与状态恢复逻辑，避免 UI 卡在旧状态
- [ ] 明确异常信息的用户态表达与日志态表达边界
- [ ] 验证 `trusted_peers` 自动接受逻辑在重启后的表现是否符合预期

### Phase 3：局域网联调与验收验证
- [ ] 在两台同局域网设备上验证 mDNS 发现是否稳定
- [ ] 验证首次配对：发起连接、响应方展示 6 位码、发起方输入后成功建立连接
- [ ] 验证已配对设备再次连接时是否能跳过配对码
- [ ] 验证文本双向同步、去重与断开后的状态回落
- [ ] 验证拒绝连接、输入错误、输入过期码、对端退出等异常路径
- [ ] 记录复现条件、日志特征与剩余问题，作为后续执行回填依据

### Phase 4：计划文档收尾与主题归档准备

- [ ] 将未完成或新发现问题整理进 `UNEXECUTED.md`

- [ ] 确认与 6.4 已锁定主题的分工关系，避免后续混淆
- [ ] 在用户确认后执行主题锁定归档

## 验收标准

- 用户能在同一局域网内看到附近设备，并从设备列表发起连接；
- 首次连接时，响应方会展示 6 位配对码，发起方输入后可成功建立连接；
- 同一对设备再次连接时，可基于已配对信息自动接受，无需再次输入配对码；
- 连接、拒绝、超时、失败、断开等提示均为自然中文，且能准确反映当前状态；
- 两台设备之间的文本剪贴板可双向同步，且不会因去重或状态残留导致明显异常；
- 主题执行结果能够在 Plans 文档中完整回填并具备归档条件。

## 风险与注意事项

- mDNS 在不同网络环境、不同系统防火墙策略下可能出现发现不稳定，需要以真实设备联调结果为准；
- LAN 体验问题往往不是“主链路缺失”，而是状态切换边界与异常提示不清，需要重点关注失败路径；
- 旧的 relay / pair 模式仍在仓库中保留，执行时要避免把 LAN 问题与旧链路问题混在一起；
- 本主题不扩展到跨网连接、公网信令、STUN/TURN 或 NAT 穿透，避免范围再次膨胀。

## 关键依赖

- `mdns-sd`：局域网服务注册与发现
- Tauri v2：桌面命令、事件、窗口与托盘集成
- TCP 直连握手与现有文本同步协议
- 本地 JSON 配置：设备身份、可信设备持久化
- 同局域网双设备实机验证环境
