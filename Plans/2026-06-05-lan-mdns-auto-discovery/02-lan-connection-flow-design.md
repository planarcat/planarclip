# 第 2 轮：局域网连接流程细化

> 时间: 2026-06-07

## 用户提问（原文）

局域网连接流程大致为：两个设备各自开启可被探查的模式，设备1查找更多设备，找到设备2，设备1向设备2发起连接申请，设备2弹出6位连接码，设备1输入连接码，设备2验证通过，建立连接

## 背景与分析

### 与第 1 轮方案的差异

第 1 轮方案对"发现后如何建立连接"的描述较为模糊，仅提到"发现设备后点击连接"，未细化连接建立过程中的交互协议。用户本次明确了完整的端到端流程，关键补充在于：

1. **双向可探查** — 不是只有一方广播、另一方浏览，而是双方都开启 mDNS 注册 + 浏览
2. **单向连接申请** — 连接有明确的发起方（Requester）和响应方（Responder）
3. **被申请方生成配对码** — 6 位码由被连接的设备生成并展示，而非发起方预设
4. **发起方输入配对码** — 类似蓝牙配对，发起方用户需要看到被申请方的屏幕，手动输入
5. **被申请方验证** — 验证权在被连接设备，而非发起方自证

### 安全模型分析

这个流程本质上是 **带外验证（Out-of-Band Verification）**：

```
设备 1（发起方）                    设备 2（响应方）
  │                                      │
  │  mDNS 发现设备 2                     │
  │                                      │
  │──── TCP 连接请求 ─────────────────→  │
  │     { device_name, peer_id }         │ 生成 6 位配对码
  │                                      │ 屏幕弹出: "PlanarClip 配对码: 870921"
  │                                      │
  │  ← 用户肉眼看到设备 2 屏幕上的码 ←   │
  │                                      │
  │  用户在设备 1 输入 "870921"          │
  │                                      │
  │──── AUTH { code: "870921" } ──────→  │
  │                                      │ 验证通过
  │←─── CONNECT_OK { session } ────────  │
  │                                      │
  │======== 加密通道建立 ===============│
```

**安全优势：**
- 防止局域网内未授权设备静默连接（必须物理可见才能配对）
- 配对码由被连接方生成，发起方无法伪造
- 与现有信令服务器的 6 位配对码机制一致，UX 统一

### TCP 连接握手协议设计

需要在 TCP 直连上定义简单的握手协议。在配对完成前，TCP 连接处于"待验证"状态，仅接受握手消息：

```
// 握手阶段的消息类型（在 TCP 直连上，验证完成前）
enum HandshakeMessage {
    // 发起方 → 响应方：申请连接
    ConnectRequest {
        device_name: String,     // 发起方设备名
        peer_id: String,         // 发起方公钥指纹（前 6 位）
        protocol_version: u8,    // 协议版本
    },
    
    // 响应方 → 发起方：等待输入配对码（可选，UI 层面已展示）
    AwaitCode,                   // 仅作为协议确认，告知发起方可以开始输入
    
    // 发起方 → 响应方：提交配对码
    AuthCode {
        code: String,            // 6 位数字码
    },
    
    // 响应方 → 发起方：验证结果
    AuthResult {
        success: bool,
        session_token: Option<[u8; 32]>,  // 验证通过后的会话令牌
    },
}
```

**但有一个简化可能**：响应方弹出配对码后，发起方用户肉眼看到并输入，发起方直接发送 `AuthCode`，无需 `AwaitCode` 中间步骤。协议可精简为：

```
ConnectRequest → AuthCode → AuthResult
```

### 配对码生成

复用现有 `crypto/keys.rs` 中的 6 位配对码生成逻辑（从 X25519 公钥指纹提取），或使用随机 6 位数字。建议：

- **临时随机码**：每次连接申请生成新的随机 6 位数字，60 秒过期
- 不直接复用设备公钥指纹，因为指纹是长期不变的，可能被局域网内攻击者重放

### 前端交互设计更新

相比第 1 轮的设计，需要在"被申请方"增加配对码弹窗：

```
发起方 UI                          响应方 UI
┌────────────────────────┐       ┌────────────────────────┐
│  PlanarClip            │       │  PlanarClip            │
│                        │       │                        │
│  📡 局域网设备         │       │  ⚠ 连接申请           │
│  ┌──────────────────┐ │       │  ┌──────────────────┐  │
│  │ 🖥 My-Desktop    │ │       │  │ My-Laptop 请求   │  │
│  │    [连接]        │ │       │  │ 连接到本设备     │  │
│  └──────────────────┘ │       │  │                  │  │

│  └──────────────┘     │
└────────────────────────┘
```

## 建议与回答

### 推荐方案

采用上述 TCP 握手协议（ConnectRequest → AuthCode → AuthResult 三段式），被申请方生成临时随机 6 位配对码。

### 与现有 pair 命令的关系

| 场景 | 配对方式 | 配对码来源 |
|:---|:---|:---|
| 局域网发现连接 | 新流程（被申请方生成码） | 被申请方随机生成，60s 过期 |
| 手动输入配对码（远程） | 现有 pair 命令 | 从公钥指纹提取，长期有效 |

两种场景可在同一个 UI 中展示，区分标识即可。

### 实现影响

- `network/direct.rs` 中的 TCP 直连模块需要增加握手状态机
- 前端需要新增：被申请方的"连接申请弹窗"（含配对码展示）、发起方的"输入配对码"界面
- `lib.rs` 需要新增 Tauri 命令：`accept_connection`、`reject_connection`、`submit_pairing_code`

## 本轮要点

- 确定局域网连接流程为：双向可探查 → 单向发起申请 → 被申请方弹出 6 位配对码 → 发起方输入 → 被申请方验证 → 建立连接
- TCP 握手协议三段式：ConnectRequest → AuthCode → AuthResult
- 配对码使用临时随机 6 位数字（非公钥指纹），60 秒过期
- 前端需为响应方增加"连接申请弹窗"，为发起方增加"输入配对码"界面
- 与现有 pair 命令共存：局域网用临时随机码，远程用指纹提取码
