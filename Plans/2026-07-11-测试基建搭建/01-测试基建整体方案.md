# 第 1 轮：怎么搭建测试基建

> 时间: 2026-07-11

## 用户提问

怎么搭建测试基建

## 背景与分析

### 当前测试基建现状（仓库扫描结果）

- 根 `package.json`、`Apps/package.json`、`Apps/src-tauri/Cargo.toml` **都没有**任何测试相关依赖或脚本
- `Apps/src` 下没有任何 `*.test.*` / `*.spec.*` 文件
- 无 `vitest.config.*` / `jest.config.*` / `playwright.config.*`
- `Apps/src-tauri/src/**` 没有独立的 `tests/` 目录，也没看到 `#[cfg(test)]` 内联测试
- Plans 里已归档的 `2026-06-04-single-machine-connection-testing` 是**手动联调**方案，不是自动化测试

结论：**测试基建完全空白**，需要从零搭建前端单测、Rust 单测 / 集成测试、以及 E2E 三层。

### 项目特性对测试选型的约束

- 桌面栈：Tauri 2（Rust 后端 + React 18 + Vite 8 前端），核心业务逻辑（配对、密钥派生、mDNS 发现、TCP 直连、剪贴板同步、去重）**都在 Rust 侧**
- 前端主要是 UI 装配层与 IPC 桥接，纯逻辑集中在 `app/utils/` 与 `app/hooks/`
- 存在跨设备协议（`peer:*` 回应码、6 位配对码、x25519 密钥交换），非常适合**协议回归测试**
- pnpm workspace，脚本命名遵循 `pnpm <动作>` / `pnpm <动作>:web` 惯例
- 前端开发端口 1420 / HMR 1421，直连端口 19876

## 建议与回答

### 分层策略（由简到难）

#### 第 1 层：Rust 单元测试（成本最低、收益最高）

Rust 自带 `cargo test`，**起步不需要新依赖**。优先覆盖：

| 模块 | 建议测试点 |
|---|---|
| `src-tauri/src/crypto/` | 密钥生成、设备指纹稳定性、X25519 派生 |
| `src-tauri/src/sync/` | 剪贴板去重逻辑、消息序列化 / 反序列化 |
| `src-tauri/src/clipboard/` | 历史摘要生成、大小 / 类型判定分支 |
| `src-tauri/src/storage/` | JSON 配置的默认值、迁移、损坏文件回退 |
| `src-tauri/src/network/` | 报文帧编解码、`peer:*` 回应码映射（协议契约，回归价值最高） |

**落地方式**：在每个模块文件底部加 `#[cfg(test)] mod tests { ... }`；跨 IO 的部分（mDNS、TCP、`arboard`）先用 trait 抽象再测。

建议加入 `[dev-dependencies]`：

```toml
[dev-dependencies]
tokio = { version = "1", features = ["macros", "rt", "test-util"] }
pretty_assertions = "1"
insta = "1"          # 快照测试，适合协议报文 / 配置结构
tempfile = "3"       # storage 测试用临时目录
```

#### 第 2 层：Rust 集成测试（协议 & 双端联调）

在 `Apps/src-tauri/tests/` 下新建集成测试，`cargo test` 会自动发现。关键场景：

- **配对协议双向握手**：同一进程内起两个 `sync` 引擎实例，走完 6 位码 → 交换公钥 → 建立会话
- **端口直连回环**：`tokio::net::TcpListener` bind `127.0.0.1:0`，两端跑真实报文，验证文本 / 图片 / 文件三条通路
- **异常路径**：连接中断、密钥不匹配、超大文件、非法帧、`peer:handled` 映射

这一层直接替代目前"两台真机来回复制粘贴"的手工联调，是**最能省时间的一层**。

#### 第 3 层：前端单测（Vitest + RTL）

Vite 8 生态首选 **Vitest**，配置几乎零成本（复用 `vite.config.ts`）。

补充 `Apps/package.json` 的 `devDependencies`：

```json
"vitest": "^2.1.0",
"@vitest/ui": "^2.1.0",
"@testing-library/react": "^16.1.0",
"@testing-library/jest-dom": "^6.6.0",
"@testing-library/user-event": "^14.5.2",
"jsdom": "^25.0.0"
```

新增文件：

- `Apps/vitest.config.ts`（`environment: "jsdom"`、`setupFiles: ["./src/test/setup.ts"]`）
- `Apps/src/test/setup.ts`：加载 `@testing-library/jest-dom`，**mock `@tauri-apps/api`**
- `Apps/src/test/tauri-mock.ts`：把 `invoke` / `listen` / `emit` 替换成可编程 stub

优先覆盖：

| 目标 | 类型 |
|---|---|
| `app/utils/*.ts`（时间 / 消息 / 设备 / 设置） | 纯函数单测 |
| `app/hooks/usePairingCountdown.ts`、`useOverlayLifecycle.ts` | Hook 测试（`renderHook`） |
| `PairingModal` / `IncomingConnectionPrompt` / `StatusNotice` | 组件测试（配合 tauri mock） |

注意：`App.tsx` 装配层测试价值低维护高，不优先覆盖。

#### 第 4 层：E2E（可延后）

Tauri 2 的 E2E 两条路：

1. **`tauri-driver` + WebdriverIO**（官方推荐，Windows 依赖 `Microsoft.WebDriver`）——真正启动打包后的应用
2. **Playwright + `pnpm dev:web`**（仅测浏览器模式 UI）——搭建 30 分钟，无法测 IPC / 剪贴板 / 发现

建议：**先做方案 2** 覆盖 UI 冒烟（三栏切换、配对弹层打开、设置项持久化到 mock storage），等前 3 层稳定后再上 `tauri-driver`。

### 脚本 & 目录约定

延续现有 `pnpm <动作>` / `pnpm <动作>:web` 命名：

**根 `package.json`：**

```json
"test": "pnpm --filter planarclip test",
"test:web": "pnpm --filter planarclip test:web",
"test:rust": "cargo test --manifest-path Apps/src-tauri/Cargo.toml",
"test:watch": "pnpm --filter planarclip test:web:watch"
```

**`Apps/package.json`：**

```json
"test": "pnpm test:web && cargo test --manifest-path src-tauri/Cargo.toml",
"test:web": "vitest run",
"test:web:watch": "vitest",
"test:web:ui": "vitest --ui"
```

**目录：**

```
Apps/
├── src/
│   ├── test/                              # 前端测试 setup + mocks
│   │   ├── setup.ts
│   │   └── tauri-mock.ts
│   └── **/__tests__/*.test.ts(x)          # 组件 / hook / util 就近放测试
└── src-tauri/
    ├── src/                                # #[cfg(test)] mod tests 内联
    └── tests/                              # 跨模块集成测试
```

`Apps/.gitignore` 加 `coverage/`。

### 落地节奏（3 步走）

| 步骤 | 内容 | 预估工作量 |
|---|---|---|
| **Step 1** | 加 `[dev-dependencies]`，为 `crypto` / `storage` / `sync` 三个模块写 10~15 条 Rust 单测；接通 `pnpm test:rust` | 半天 |
| **Step 2** | 引入 Vitest + RTL，加 tauri mock，先测 `utils/` 和 2~3 个 hook；接通 `pnpm test:web` | 半天 |
| **Step 3** | 在 `src-tauri/tests/` 加协议集成测试（回环 TCP + 配对握手 + 文件传输）| 1~2 天 |

E2E（第 4 层）等前三步稳定后再评估。

### 待用户确认的决策点

1. **前端框架**：Vitest（推荐）还是 Jest？
2. **覆盖率门禁**：是否在 `pnpm test:web` 加 `--coverage` 并卡 60% 阈值？
3. **E2E 优先级**：先 Playwright 浏览器冒烟，还是直接上 `tauri-driver`？
4. **CI**：是否顺手加 `.github/workflows/` 跑 `pnpm check && pnpm test`？

## 本轮要点

- 仓库测试基建**完全空白**，需从零搭建三层：Rust 单测 / Rust 集成 / 前端 Vitest；E2E 延后
- **优先级顺序**：Rust 单测 → 前端 Vitest → Rust 集成 → E2E；Rust 层价值最高（核心业务在 Rust）
- 脚本命名沿用 `pnpm test` / `pnpm test:web` / `pnpm test:rust`，遵循仓库既有 `<动作>` / `<动作>:web` 惯例
- Rust 集成测试用 `127.0.0.1` 回环 + 同进程双引擎，替代目前手工双机联调
- 前端必须 mock `@tauri-apps/api`（`invoke` / `listen` / `emit`），否则组件测试会因找不到 IPC 报错
- 4 个决策点待用户确认：前端框架、覆盖率门禁、E2E 优先级、是否加 CI
