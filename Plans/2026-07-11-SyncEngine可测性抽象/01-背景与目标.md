# 第 1 轮：什么是 SyncEngine 可测性抽象、要不要现在做

> 时间: 2026-07-11

## 用户提问

什么是 SyncEngine 可测性抽象？（用户后续追问「需要做」）

## 背景与分析

### 起因

在上一主题 `2026-07-11-测试基建搭建` 的 Phase 4 里，原方案计划做 `clipboard_sync_e2e`：起两个同进程的 `SyncEngine` 实例 + 一个内存 `ClipboardSource`，验证「本地剪贴板事件→广播到所有连接」的分派逻辑。落地时发现 `SyncEngine::new` 强制要求 `AppHandle: tauri::AppHandle`，测试里根本构造不出，遂转入 UNEXECUTED。

### `SyncEngine` 现状

`Apps/src-tauri/src/sync/engine.rs` 一共 133 行，结构极简：

```rust
pub struct SyncEngine {
    rx: broadcast::Receiver<ClipboardEvent>,
    connections: Arc<Mutex<ConnectionRegistry>>,
    transfer_slots: Arc<TransferSlotLimiter>,
    config: Arc<Mutex<AppConfig>>,
    app_handle: AppHandle,               // ← 无法在单元测试中构造
}

impl SyncEngine {
    pub fn new(rx, connections, transfer_slots, config, app_handle) -> Self { ... }
    pub async fn run(mut self) { loop { rx.recv() → broadcast_snapshot(...) } }
    fn broadcast_snapshot(handles: &[ConnectionHandle], snapshot, ..., app_handle) { ... }
}
```

`broadcast_snapshot` 内的 3 处分派全部走 `ConnectionHandle::{send_snapshot, send_image_async, send_files_async, supports_chunked_images}`，且这些方法都**要 `AppHandle`**（tauri emit 事件用）。

### 什么叫"可测性抽象"

把 SyncEngine 依赖的**具体运行时对象**（`AppHandle` + `ConnectionHandle`）藏到一个 **trait** 后面，让测试能塞一个内存假实现进去。核心 trait 大致长这样：

```rust
pub trait ClipboardOut: Send + Sync {
    fn supports_chunked_images(&self) -> bool;
    fn send_snapshot(&self, snapshot: &ClipboardSnapshot, sync_images: bool);
    fn send_image_async(&self, snapshot: ClipboardSnapshot, sync_images: bool);
    fn send_files_async(&self, snapshot: ClipboardSnapshot, sync_files: bool, max_file_bytes: u64);
}
```

生产实现 `TauriConnectionOut { inner: ConnectionHandle, app: AppHandle }` 把两个真身包起来；测试实现 `InMemoryOut { sent: Arc<Mutex<Vec<_>>> }` 直接记录被发送的内容，用于断言。

### 为什么值得做

- **回归价值**：SyncEngine 是本机→他机的**分派中枢**，一旦"哪些内容 / 什么类型 / 什么开关下 走哪条通道"逻辑改错，直接影响用户所有同步行为
- **成本可控**：`sync/engine.rs` 只 133 行，唯一构造点在 `lib.rs:3219`，`ConnectionHandle` / `webrtc.rs` **一行不动**
- **护栏效应**：之后要加"仅同步纯文本模式""按内容类型分流"这类新分派规则时，能直接用测试驱动，不用双机手工回归

### 为什么风险要提前分析

- `SyncEngine::new` 签名要改（多一个 trait object 参数），`lib.rs` 唯一构造点要同步改
- `broadcast_snapshot` 里的 `AppHandle` 依赖要被彻底移到 trait 后面
- 生产路径必须**行为 100% 等价**——大图 chunked、文件 batch、内联小图、纯文本，四条分派分支都要对齐

按 AGENTS.md 与 development-guardrails，动这个改动前必须先出方案 + 用户确认。

## 建议与回答

**结论：值得做，但按"抽象 → 保证等价 → 加测试"三步走**，不要边抽象边加新特性。

- 本主题只做**抽象 + 生产等价**这一步；`clipboard_sync_e2e` 测试作为附带产物加进去，验证抽象是否成功
- 不改 `ConnectionHandle` / `webrtc.rs`
- 不引入新分派逻辑（比如按 peer 优先级、按内容类型开关）
- 完成后作为独立主题归档，供未来引用

## 本轮要点

- SyncEngine 可测性抽象 = 用 `ClipboardOut` trait 把 SyncEngine 与 `AppHandle` / `ConnectionHandle` 解耦
- 目标是让 `clipboard_sync_e2e` 能在毫秒级、无 Tauri 运行时地验证广播分派
- 用户确认「需要做」，作为独立主题落盘
- 本主题只做抽象 + 等价保证，不带新特性
