# 第 4 轮：那暂时不用考虑跨网

> 时间: 2026-06-04 09:13

## 用户提问

那暂时不用考虑跨网

## 背景与分析

这是一个范围收敛决策，意味着当前阶段不再把“不同网络之间的自动互联”作为设计目标。

这会直接影响当前方案的技术边界：

- 不需要现在就设计公网 signalling / STUN / TURN；
- 不需要现在处理 NAT 穿透、跨网重连、异地设备发现；
- 可以把注意力集中在：
  - 单机双实例测试；
  - 同局域网设备发现；
  - 局域网内直连同步；
  - 基础身份校验与回环去重。

对 PlanarClip 当前阶段来说，这个收敛是合理的，因为：

1. 当前代码本来就还在 MVP 骨架阶段；
2. 先把局域网/单机链路跑通，能更快验证产品核心价值；
3. 跨网一旦加入，会把问题复杂度提升一个层级；
4. 未来如果需要跨网，再在局域网能力之上扩展，会比一开始就同时做两条主路径更稳。

但也要认识到，这个决策只是“暂时不考虑”，不是永久否定跨网。后续若产品定位升级为“个人多设备同步工具”，仍可能需要重新打开跨网议题。

## 建议与回答

可以，当前阶段完全可以把目标收敛为：

### 当前只做两层能力

1. **单机双实例测试**
   - 验证连接链路、消息收发、剪贴板同步。

2. **同局域网设备直连**
   - 作为后续无第三方方案的主方向。

### 当前明确不做的内容

先不考虑：

- 公网 signalling 部署
- WebRTC 跨 NAT
- STUN / TURN
- 异地设备自动发现
- 跨网络断线重连策略

### 当前最合理的推进顺序

1. 先把本地 relay + 双实例测试跑通；
2. 再讨论局域网下“自动发现还是手动输入地址”；
3. 然后决定局域网直连的数据通道方案；
4. 最后再做局域网模式的 UI 和配对体验。

这会比同时背负跨网设计负担更清晰。

## 本轮要点

- 当前阶段正式收敛范围：暂不考虑跨网。
- 当前重点转为单机测试与局域网内直连能力。
- 暂不处理 signalling/STUN/TURN/NAT 穿透等跨网问题。
- 未来若产品定位变化，可再重新开启跨网方案讨论。
