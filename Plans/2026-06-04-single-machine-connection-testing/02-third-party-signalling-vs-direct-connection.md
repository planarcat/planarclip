# 第 2 轮：也就是说，必须要有一个第三方担当信令服务器角色？有没有不需要第三方的方案，只要两个设备安装了应用就可以互相通信

> 时间: 2026-06-04 09:06

## 用户提问

也就是说，必须要有一个第三方担当信令服务器角色？有没有不需要第三方的方案，只要两个设备安装了应用就可以互相通信

## 背景与分析

这个问题本质上是在问：**两台设备如何在完全没有第三方中介的情况下相互发现并建立连接。**

先把“第三方”分开看：

1. **第三方云服务器 / 公共服务器**
   - 例如公网 WebSocket signalling server、云 TURN、公共配对服务。
2. **第三方发现机制**
   - 哪怕没有云服务器，只要借助局域网广播、手工输入 IP、扫码交换地址，本质上仍然需要某种“发现路径”。

关键结论是：

- **不是必须依赖第三方云服务器。**
- 但**必须有一种让双方“知道彼此怎么连”的机制**。
- 如果没有中心服务器，就得改成“端到端自主发现”或“人工交换连接信息”。

从网络原理上看，两台设备直接通信要满足两件事：

1. **发现对方**：知道对方在哪儿（IP、端口、局域网身份、蓝牙身份等）；
2. **建立链路**：至少有一种底层通道可用（TCP、UDP、蓝牙、局域网 socket）。

所以“不需要第三方”的方案是存在的，但通常都有前提条件或体验代价。

---

### 可行方案分类

#### 方案 A：局域网自动发现 + 直连

思路：

- 两台设备都在同一局域网；
- 应用启动后通过 mDNS / UDP 广播宣布自己存在；
- 对方收到广播后显示“发现设备”；
- 用户点击连接，之后走本地 TCP / UDP / WebRTC-LAN 直连。

优点：

- 不依赖云服务器；
- 同一 Wi‑Fi / 局域网下体验最好；
- 真正接近“装上就能互相看到”。

缺点：

- 仅适用于同一局域网；
- 跨网段、公司网络、访客网络下可能被限制；
- Windows / macOS 上广播与发现的兼容性要额外验证。

#### 方案 B：手工输入 IP/端口直连

思路：

- A 显示自己的局域网 IP 和监听端口；
- B 手工输入 `192.168.x.x:port` 连接；
- 连接成功后两端直接同步。

优点：

- 完全不需要第三方；
- 实现最直接；
- 非常适合作为开发阶段或应急连接模式。

缺点：

- 用户体验一般；
- IP 可能变化；
- 只适合局域网或已知可达网络。

#### 方案 C：二维码 / 配对码交换直连信息

思路：

- A 生成包含地址、公钥、端口等信息的二维码或短码；
- B 扫码或输入后直接连接；
- 不依赖中心服务器，但依赖“人工搬运连接信息”。

优点：

- 不需要云端中介；
- 比手输 IP 体验好；
- 更容易附带公钥做安全绑定。

缺点：

- 桌面端扫码不一定方便；
- 若地址不可达，仍然会失败；
- 对跨 NAT 网络无能为力。

#### 方案 D：蓝牙 / 局域网混合发现

思路：

- 先通过蓝牙、Nearby、Bonjour 等本地能力发现设备；
- 再切换到局域网 socket 或其他高吞吐通道传输剪贴板。

优点：

- 比纯手工输入更自然；
- 不依赖公网服务；
- 适合“附近设备”配对体验。

缺点：

- 跨平台实现复杂；
- Tauri + Rust 在这部分的生态与调试成本较高；
- MVP 不适合先走这条路。

#### 方案 E：纯公网直连、完全无第三方

理论上如果两台设备都能直接暴露公网地址，并且用户能交换这些地址，就能完全无第三方直连。

但现实里：

- 家庭宽带、公司网络、移动热点普遍有 NAT；
- 没有 STUN/TURN/信令时，很难自动建连；
- 桌面应用用户也不可能手动做端口映射。

因此该方案**理论可行，产品上几乎不可用**。

---

### 对 PlanarClip 的现实判断

如果目标是：

> 只要两个设备安装了应用，就可以互相通信

那么这句话通常隐含了两个要求：

1. 用户不需要手输网络参数；
2. 设备不一定在同一局域网。

在这种要求下，**几乎一定需要某种外部协助**，最常见就是：

- signalling server
- STUN / TURN
- 配对信息中转服务

如果你愿意接受约束：

> 只要两个设备在同一局域网，就可以互相通信

那就可以设计成**不需要第三方云服务器**，走：

- mDNS / UDP 广播发现
- 局域网 TCP/UDP 直连

这才是最现实的“去第三方”方案。

## 建议与回答

结论分两层：

### 结论 1：不是必须有“第三方云服务器”

如果你接受以下限制之一：

- 两台设备必须在同一局域网；
- 用户需要手动输入 IP / 配对信息；
- 只做局部网络内使用；

那就可以做到**没有第三方云服务器**。

### 结论 2：但不能没有“发现与建连机制”

即使没有第三方，你仍然需要以下至少一种：

- 局域网广播发现；
- 手工输入地址；
- 扫码交换连接信息；
- 蓝牙 / Nearby 发现。

所以真正能做到的是：

- **无第三方服务器**：可以；
- **无任何额外发现机制**：不可以；
- **只装应用就自动跨网络互连**：通常不现实。

### 对当前项目最适合的无第三方方向

对于 PlanarClip 当前阶段，最值得考虑的是两条路线：

#### 路线 1：保留现有 signalling 方案作为默认模式

适合：

- 跨网络设备；
- 未来生产环境；
- 用户零配置体验。

#### 路线 2：新增“局域网直连模式”作为无第三方补充

建议设计为：

- 同网段下自动发现设备；
- 点击后直接连接；
- 同步文本剪贴板；
- 不经过公网服务器。

这条路线最符合“两个设备装好应用就能互相通信”的直觉，但前提是**同一局域网**。

### 推荐决策

如果从产品路线看，建议采用双模式：

1. **默认模式：信令服务器配对**
   - 覆盖跨网络使用；
   - 作为主路径。
2. **局域网模式：自动发现直连**
   - 覆盖无第三方、同网段快速使用；
   - 作为增强路径。

这样既保留可用性，也兼顾“去第三方”的诉求。

## 本轮要点

- 不一定必须依赖第三方云服务器。
- 但一定需要某种发现和建连机制。
- 真正可落地的无第三方方案，最适合的是“同局域网自动发现 + 直连”。
- 想做到跨网络零配置互连，通常仍需信令/STUN/TURN 等外部协助。
- 对 PlanarClip，推荐“服务器模式 + 局域网直连模式”双路线。
