### 真实差距重估

#### 1. Make 产物现在更接近产品，但仍不是可直接上线的前端

虽然 Make 项目已经带有配对弹层、设备页和设置页，但它的问题仍然存在：

- 设备数据仍是 mock；
- 局域网发现列表仍是模拟数据；
- 配对流程是前端 `setTimeout` 演示，不是真连接；
- 设备移除、同步开关、最近同步记录都还没有真实后端约束。

#### 2. 新方案不能再停留在“把 Figma 项目搬进去”这个层级

由于 Make 已经演化出不少 UI 逻辑，本轮方案必须升级为：

- **保留其布局与组件结构**；
- **剥离其所有伪业务状态**；
- **建立一层真实的桌面应用状态模型**；
- **由 Tauri commands/events 驱动整个 React UI**。

#### 3. 节点 `1:1121` 给出的一个重要信号

既然当前指定节点是“设置页激活态”，说明执行时不能只优先做剪贴板页，而应把以下三块作为同一轮重构边界一起考虑：

- 左侧导航壳层；
- 设备管理页；
- 设置页；
- 配对弹层；
- 剪贴板页可先做真实简化版，但不能缺席。

换句话说，本轮 UI 重构应当是**整壳重构**，而不是只改一个页面。

## 建议与回答

我建议采用下面这个方案：

### 推荐方案：Design 定稿 + Make 落地 + 当前应用宿主接管

这是本轮推荐的唯一主方案：

1. **以 Figma Design 节点结构作为最终视觉依据**；
2. **以当前最新 Make 项目作为前端实现脚手架**；
3. **将前端代码迁入 `Apps/planarclip`，由当前 Tauri 工程继续承载运行**；
4. **对 Make 中的 mock 业务状态做系统性替换，而不是打补丁式修修补补**。

### 为什么推荐这条路线

#### 原因 1：Design 比 Make 更可靠

- Design 才是你当前确认过的真实设计稿；
- Make 是根据某一时刻设计生成的代码近似物；
- 当二者不一致时，应始终以 Design 为准。

#### 原因 2：Make 比从零重写更省力

- 既然 Make 已经产出了相当完整的 React/Tailwind 页面，没必要从空白组件重新搭界面；
- 但不能原样照搬业务逻辑，否则后面接真实状态时会越接越乱。

#### 原因 3：当前桌面能力不能被替换掉

- 托盘、窗口、配对命令、设备发现、连接事件都在 `Apps/planarclip/src-tauri`；
- 真正要重构的是前端表现层，不是整个产品工程。

### 实施策略：三层拆分

#### Layer A：视觉壳层

目标：把当前桌面应用的外壳彻底换成 Design/Make 的新结构。

包括：

- 整体三栏布局；
- 左侧导航；
- 剪贴板页容器；
- 设备页容器；
- 设置页容器；
- 配对弹层；
- Toast/状态提示区。

这一层允许先用占位态，但布局和组件拆分要一次成型。

#### Layer B：前端状态适配层

目标：建立一个专门承接 Tauri 的前端桥接层，把“Rust 世界”和“React 世界”隔开。

建议它负责：

- 封装 `invoke` 命令；
- 封装 `listen` 事件；
- 管理当前连接状态、待配对状态、LAN 设备列表；
- 维护本机会话级剪贴板历史；
- 管理弹层开关、错误提示、按钮禁用态；
- 把原始后端数据映射为 UI ViewModel。

#### Layer C：后端补口层

目标：只在必要时补最少量的 Rust/Tauri 接口，使新 UI 不再靠 mock 数据演戏。

优先补这些：

- 读取当前配置（设备名、端口、LAN 开关等）；
- 更新基础设置项；
- 提供当前连接摘要；
- 提供已信任设备列表；
- 提供会话级最近剪贴板记录或最近同步摘要。

### 推荐执行顺序

#### Phase 1：前端骨架迁移

先做这些：

- 把 `Apps/planarclip` 从现有 DOM 页面切到 React 入口；
- 引入 Make 项目的 `src/app` 与 `src/styles` 作为新前端主体；
- 对照 Design 节点 `1:1121` 校正当前 Make 结构，确保导航选中态、设置页布局、配色与层级一致；
- 统一构建配置到新的 React/Vite 方案；
- 调整 Tauri 窗口尺寸，适配桌面控制台布局。

#### Phase 2：接回连接主链路

优先打通当前已经存在的真实能力：

- `get_status`
- `get_pairing_code`
- `get_lan_devices`
- `connect_lan`
- `submit_pairing_code`
- `reject_connection`
- `disconnect`
- `connection-*` 事件
- `lan-devices-changed`

重点是：

- 用真实事件替换 `PairingModal` 里的模拟 `setTimeout` 流程；
- 用真实 LAN 设备列表替换 `DISCOVERED` mock；
- 用真实连接状态替换设备页、侧边栏、状态提示中的演示状态。

#### Phase 3：把设置页从“展示稿”变成“可用页”

设置页是这次指定 Design 节点的重点，因此不建议再把它放进“以后再说”的角落。

本期至少要实现：

- 背景模式切换（前端即可落地）；
- 主题色切换（前端即可落地）；
- 与后端相关的设置项梳理为“真实可改”和“暂不支持”两类；
- 为真实可改项补接口；
- 对暂不支持项使用禁用态或说明文字，而不是伪开关。

#### Phase 4：剪贴板页做真实收敛

剪贴板页不要求一次做到图片/文件真同步，但至少需要：

- 保留列表/网格视图切换；
- 展示会话内文本记录或最近同步摘要；
- 明确哪些记录来自真实同步，哪些仍是占位；
- 去掉误导性的远程图片示例和假文件记录。

#### Phase 5：产品收口

最后再做：

- 用户可见文案统一中文；
- 配对成功/失败/拒绝/断开等反馈统一风格；
- 托盘打开窗口后的状态恢复；
- 响应式边界与最小窗口尺寸；
- 未支持能力进入空态或未来版本清单。

### 本轮推荐结论

如果现在开始实施，我推荐执行边界如下：

#### 本轮必须做

- 用最新 Design + Make 重构 `Apps/planarclip` 的整体前端壳；
- 打通导航、设备页、设置页、配对弹层；
- 把当前连接主链路完整接入新 UI；
- 把 mock 连接数据替换成真实后端状态；
- 为设置页补一批最小必要接口；
- 调整桌面窗口尺寸与布局。

#### 本轮不建议强行做满

- 图片同步真链路；
- 文件同步真链路；
- 历史剪贴板全量持久化；
- 跨网连接、STUN/TURN、NAT 穿透；
- 所有设置项都做成真实可写。

### 风险判断

- **中高风险：前端技术栈切换** — 从原生 DOM 迁到 React，是结构性改造；
- **中高风险：Make 逻辑去 mock 化** — 不能只替换几个变量，而是要拆掉一层假状态系统；
- **中风险：设置页需求膨胀** — 设计稿会让用户觉得所有开关都可用，需要产品边界说明；
- **中风险：窗口形态变化** — 新界面天然更像桌面控制台，小窗口体验需重新定义。
